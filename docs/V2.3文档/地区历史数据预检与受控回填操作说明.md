# 地区历史数据预检与受控回填操作说明

更新日期：2026-09-03。适用脚本：`backend/scripts/backfill-v23-route-regions.ts`，报告格式版本 2。

## 1. 范围与安全边界

- 只处理未删除的官方路线和 `status=1` 的骑友路线的地区字段、点位地区、地区覆盖表。
- 不调用逆地址解析，不使用腾讯地图 Key，不根据地址文字或当前浏览城市猜测归属。
- 不修改用户资料、微信号、路线可见性、图片、外部链接、已有折线；原脚本附带的重复微信号检查不再属于地区回填流程，需要时单独进行账号审计。
- 已有点位仅补齐有明确来源的地区字段，保留点位 ID、顺序、名称和坐标，不删除后重建已有点位。
- 骑友路线没有结构化点位时，可依据旧起点和途经点字段生成；旧终点只有名称/坐标而没有城市时，整条记录拦截，须先人工确认。
- 地市目录、区县父子关系、粗略坐标范围、点位结构和主归属一致性全部通过，才允许重建覆盖表。粗略范围不是精确行政区边界证明。
- 任一点位缺少城市、代码非法、两套点位快照冲突时，整条记录保持原样，不进行部分覆盖重建。

## 2. 只读预检

在 `backend/` 目录执行：

```bash
npm run db:backfill:v23:preview
```

脚本使用该环境的 `DATABASE_URL`。执行前须确认目标环境；不要在聊天、命令日志或文档中粘贴连接串。

预检不写数据库，但会在 `backend/logs/v23-region-backfill/preview-<随机后缀>/` 下生成本地报告。也可指定报告根目录：

```bash
npm run db:backfill:v23:preview -- --report-dir /absolute/path/to/private-reports
```

每次运行创建独立目录，不覆盖已有报告。目录默认仅当前用户可访问，报告文件权限为 0600。默认目录被 Git 忽略，不应提交报告到公开仓库。

| 文件 | 内容 |
| --- | --- |
| `summary.json` | 模式、目录版本、扫描数量、各状态计数、是否异常中断 |
| `results.jsonl` | 每条路线的类型/ID、处理状态、错误代码和点位序号 |
| `checkpoint.json` | 已核验记录指纹、数据库标识哈希、模式和版本，用于续跑 |

报告不包含地址、坐标、用户标识、数据库连接串或原始 Prisma 错误。资源键示例 `user:1` 表示骑友路线 ID=1；`official:1` 表示官方路线 ID=1。`order` 为数据库点位顺序（通常从 0 开始），不是用户页面中的自然序号。

## 3. 结果和退出码

| 状态 | 含义 |
| --- | --- |
| `ready` | 预检通过，需要回填；未写入 |
| `unchanged` | 当前地区数据与目标一致，不需要写入 |
| `applied` | 已在单条路线事务内写入并复核通过 |
| `resumed` | 与同模式检查点中的已核验指纹一致，跳过重复操作 |
| `blocked` | 缺少城市、非法数据或快照冲突，保留原记录，需人工修正 |
| `failed` | 查询/事务失败或并发修改，未标记完成，后续重试 |

- 退出码 `0`：本次扫描无拦截或失败。
- 退出码 `2`：扫描完成，但存在待处理或失败记录；不能视为全量修复成功。
- 退出码 `1`：参数、检查点、数据库扫描或报告写入等运行级异常。

常见问题代码：

| 代码 | 处理办法 |
| --- | --- |
| `missing_city` | 用户重新选点或运营明确确认该点城市；不能沿用起点/浏览城市 |
| `unsupported_city` / `unsupported_province` | 核查是否确实为非新疆历史样例，不自动改为新疆 |
| `district_city_mismatch` | 确认区县所属地市；无法确认时通过正常编辑流程清空区县 |
| `invalid_coordinates` | 重新选点核对；不要修改坐标以“通过校验” |
| `primary_city_conflict` / `primary_district_conflict` | 主归属与起点显式地区冲突，先由用户或运营确认 |
| `start_snapshot_conflict` / `end_snapshot_conflict` / `waypoint_snapshot_conflict` | 旧字段与结构化点位不一致，通过正常编辑流程统一，不猜测哪个版本正确 |
| `invalid_waypoint` / `invalid_waypoints` / `invalid_point_order` | 核查旧数据格式与顺序，不静默丢弃点位 |
| `resource_changed` | 预检后记录发生变更/删除，重新预检，不覆盖新内容 |
| `post_write_verification_failed` | 事务内复核失败，回滚该记录并检查实现 |

## 4. 断点续跑

使用上一轮输出的实际目录路径：

```bash
npm run db:backfill:v23:preview -- --resume /absolute/path/to/previous-preview-directory
```

续跑规则：

1. 校验报告格式、行政区目录版本、数据库哈希和运行模式，任一不匹配则拒绝。
2. 按 ID 每批最多 100 条重新扫描索引、逐条读取数据，不一次加载所有路线。
3. 已核验且相关数据指纹未变的记录跳过；被修正的、失败的和新增的记录重新检查。
4. 当前记录的报告写入后，原子替换检查点文件；中断后可从最后成功保存的检查点继续。
5. 续跑写入一个新目录，保留上次证据。事务提交后、检查点保存前中断时，下一轮会发现数据已一致，避免重复改写。

这不是“跳过某个 ID 以前的所有数据”：未解决记录不会因续跑而永久遗漏。预检检查点不能用于 apply，以免把“只检查过”误当“已写入”。

## 5. 受控 apply（本轮未执行）

执行前必须完成：目标环境确认、数据库备份可恢复性检查、待处理项人工确认、预检报告审核，并取得目标环境的数据变更授权。生产建议维护窗口执行。

确认后在同一环境运行：

```bash
npm run db:backfill:v23:apply
```

等价于脚本参数 `--apply V23-BACKFILL`；错误 token 或未知参数会被拒绝。apply 仍会拦截不安全记录，但可以处理其他已通过校验的记录，因此必须审核逐条报告，不能只看命令是否结束。

恢复中断的 apply 必须使用 **apply 模式** 检查点：

```bash
npm run db:backfill:v23:apply -- --resume /absolute/path/to/previous-apply-directory
```

每条路线使用 Serializable 事务：重读并比较指纹→写入必要地区变更→再次生成计划，确认已无差异。并发变更和事务冲突会进入失败报告，不盲目重试覆盖。

完成后重跑预检，对账官方/骑友路线数量、公开列表和跨城覆盖，按项目部署流程使路线列表缓存失效。脚本自身不连接 Redis，不更改线上缓存；缓存/接口端到端验收仍是发布门禁。
