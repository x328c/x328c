# 地区筛选查询计划与本地性能报告

记录日期：2026-09-03。结论：本地隔离库性能样本通过，不能据此认定生产接口性能或完整版本验收通过。

## 测量范围与可追溯证据

- 脚本：`backend/test/region-performance.integration-spec.ts`，须显式设置 `RUN_REGION_PERF=1` 和经隔离校验的 `TEST_DATABASE_URL`。默认跳过不代表通过。
- 原始结果：`backend/logs/region-performance/run-pN9tZB/report.json`，Git 忽略；包含采样结果和实际 SQL 的 `EXPLAIN FORMAT=JSON`。
- 测试库：本机可丢弃 MySQL 8 容器 `modazi-region-20260903-test`，端口33079，数据库 `modazi_region_test`；不是现有业务库。
- 合成数据：同行10,000条、骑友路线5,000条、官方路线3,000条，分布5个城市；每个同行1个点位，每条路线3个点位，全部路线覆盖测试所选城市。
- 每场景预热5次、采样200次、并发5。边界为进程内 Service 加本地 MySQL 连接，不包含 HTTP鉴权、TLS、公网、真实 Redis 延迟或小程序渲染。
- 数据由专用测试用户/管理员创建，测试结束按其ID清理；没有修改业务记录。

## 查询计划与已实施调整

1. 同行城市查询先通过主表城市索引和点位地区索引组成候选ID集合，再用主键关联业务记录；距离、半径、优先级、分页在SQL中完成。主业务表访问为 `ref`、`eq_ref` 或当页ID的 `range`。
2. 官方仅途经查询先走 `route_regions_city_code_district_code_route_id_idx`，再按主键关联路线；按当页ID补全详情时继续校验公开状态及筛选条件。
3. 骑友关键词查询使用 `user_routes_visibility_status_created_at_id_idx` 的 `range`，覆盖关系走唯一键 `eq_ref`。索引范围仍可能较宽，不能把“没有ALL”理解为任意数据规模均高效。
4. 两个详情查询主记录均为主键 `const`。
5. 测试断言不允许被测主业务表访问方式为 `ALL`。候选ID临时表及UNION结果的 `ALL` 仍存在，是遍历已筛选候选集合，不是原始主业务表全表扫描；临时表排序成本仍需持续观察。
