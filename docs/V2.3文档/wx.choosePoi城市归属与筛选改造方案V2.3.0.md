# 摩搭子助手 V2.3.0 `wx.choosePoi` 城市归属与筛选改造方案

> **最新补充**：按随后真机反馈，支持无名称坐标；普通原生选点失败时可经用户确认进入地图自由选点。`address` 中明确的行政区前缀用于自动填写地州市，无法明确识别才手动确认，且始终可修改。此次允许受控地址匹配，覆盖此前“不解析地址”的决定；不使用 Key 逆地址解析。详见 [无名称选点与地址地区识别](./无名称选点与地址地区识别.md)。

> **2026-09-03 真机反馈修订（优先于下文原方案）**：`wx.choosePoi` 的地点列表不符合可拖动地图精确选点的体验要求。小程序同行、路线选点已恢复 `wx.chooseLocation`，选点完成后明确确认所属城市，区县选填；不再依赖 `choosePoi.city` 自动归属。仍不使用腾讯地图 Key、逆地址解析或地址字符串猜测，后台校验、地区字段与覆盖筛选保持不变。详见 [地图选点体验修复说明](./地图选点体验修复说明.md)。下文涉及 `choosePoi` 接口、自动城市识别和权限声明的内容作为历史方案保留，不再作为当前交互验收标准。

> 编制日期：2026-09-02  
> 方案修订：2026-09-03；明确删除地区识别 Key 配置，而非保留为空或临时关闭  
> 适用版本：V2.3.0 增量更新  
> 影响范围：小程序同行、骑友路线、官方路线录入、城市/地区筛选、历史数据兼容  
> 决策主题：以 `wx.choosePoi` 返回的城市名称和用户人工确认作为地区唯一来源；删除腾讯地图 Key 逆地址解析配置，不使用该技术兜底、校验或回填

## 1. 背景与问题

V2.3.0 已具备新疆城市/地区切换、同行集合点距离排序、路线起点/途经地区覆盖等能力。以下描述本次改造前的问题，不作为当前实现状态或部署结果的证明：

1. 小程序使用 `Taro.chooseLocation` 获取地点名称、地址和经纬度。
2. 客户端先将当前页面所选城市、区县写入点位 DTO 作为兜底值。
3. 原方案允许后端在腾讯地图 Key 可用时调用逆地址解析并覆盖客户端值，造成地区筛选依赖外部服务、密钥和配额。
4. 外部接口超时、配额耗尽或解析失败时，现有兜底还可能采用客户端当前选择地区，存在跨城市选点被错误归类的风险。

本次改造在用户选择地点时直接取得城市名称，无法取得时要求人工确认；地区链路彻底删除腾讯地图 Key 逆地址解析配置和调用。

## 2. 目标与非目标

### 2.1 目标

- 新建同行、骑友路线时，优先使用 `wx.choosePoi` 返回的城市名称确定地市代码。
- 地市代码使用项目现有新疆行政区划目录统一转换，不在数据库中保存自由文本作为过滤条件。
- 同行以集合点地市为主归属，同时保存途经点、终点的地市信息。
- 路线以起点地市为主归属，同时建立所有有效点位的地区覆盖索引。
- `wx.choosePoi` 未返回城市或城市无法识别时，要求用户明确选择所属城市，不静默猜测。
- 删除地区识别相关的腾讯地图 Key、逆地址解析调用、抽样复核和回填逻辑。
- 历史缺失地区通过现有代码、用户重新编辑或管理后台人工确认修复。
- 复用现有数据模型和索引，尽量不新增重复字段、不进行高风险结构迁移。

### 2.2 非目标

- 本次不实现道路级导航或实时轨迹定位。
- 本次不承诺仅通过 `wx.choosePoi` 自动识别区县；微信端主要可靠获得城市名称。
- 本次不以地址字符串拆词作为唯一地区识别依据。
- 本方案不使用腾讯地图 Key 判断、验证或修复行政区归属。
- 小程序自带地图的 `choosePoi`、地图展示和 `openLocation` 不需要把 WebService Key 暴露给小程序，仍可使用。
- 本次不改变“途经本地不代表允许中途加入同行”的业务规则。

## 3. 能力结论与约束

### 3.1 `wx.choosePoi` 可满足的能力

精确选择 POI 时，客户端可取得：

- `type`：选择城市或精确位置；创建业务点位时要求 `type === 2`。
- `name`：地点名称。
- `address`：详细地址。
- `latitude/longitude`：GCJ-02 坐标。
- `city`：城市名称，可用于映射项目内部地市代码。

因此，若筛选目标是新疆地州/市级别，`city` 足以作为主要归属来源。

### 3.2 不能单独解决的能力

- 不能稳定取得微信端的标准区县行政代码。
- 无法从服务端证明客户端提交的城市代码一定与坐标一致。
- 城市名称可能存在全称、简称、自治州简称等差异。
- 旧客户端仍可能使用 `chooseLocation`，没有 `city` 字段。
- 历史数据、后台导入数据、关联路线快照不会自动经过本次选点流程。

因此本方案采用“城市名称归一化 + 用户确认兜底 + 服务端目录校验”的封闭链路，不再设置地图复核分支，也不把 `city` 原文直接写入查询字段。

## 4. 总体方案

```text
用户进入创建页
      ↓
读取全局当前城市，作为选择器初始城市
      ↓
调用 wx.choosePoi / Taro.choosePoi
      ↓
取得 POI 名称、地址、坐标、城市名称
      ↓
城市名称归一化与别名匹配
      ├─ 匹配成功 → 生成标准 city_code
      └─ 未匹配   → 弹出所属城市确认选择器
      ↓
区县信息
      ├─ 用户有明确需要 → 从该城市下属区县中手动确认
      └─ 无法确认       → district_code 留空，不猜测
      ↓
页面展示“所属地区”，用户可修改
      ↓
随点位提交 city_code / district_code
      ↓
服务端验证代码存在及父子关系
      ↓
写入主归属字段、点位字段、路线地区覆盖表
      ↓
列表按所选城市/地区查询并排序
```

## 5. 产品规则

### 5.1 地区层级

本次将识别能力分为两个层级：

| 层级 | 数据来源 | 是否强制 | 用途 |
| --- | --- | --- | --- |
| 地州/市 | `choosePoi.city` 映射，失败时人工确认 | 强制 | 城市切换和主列表筛选 |
| 区县 | 用户从当前城市下属区县中人工确认 | 可选 | 更精细的地区筛选 |

地市级代码缺失时禁止提交；区县无法确认时允许保存为 `null`，但不能把全市内容伪造为某个区县。

### 5.2 同行归属

- 集合点的 `city_code` 写入 `rides.city_code`，作为同行主归属城市。
- 集合点的 `district_code` 写入 `rides.district_code`。
- 途经点、终点分别保存自己的 `city_code/district_code` 至 `ride_points`。
- 终点同时同步至现有 `destination_city_code/destination_district_code`。
- 城市列表查询命中集合点或任一点位即可展示。
- 排序优先级：集合点命中 > 仅途经/终点命中 > 其他排序规则。
- 在仅途经点命中时，卡片显示“途经本地”，但详情继续突出真实集合地点。

### 5.3 骑友路线归属

- 起点城市写入 `user_routes.city_code`，起点区县写入 `district_code`。
- 起点、途经点、终点均写入 `user_route_points`，每个点保存自己的地区代码。
- 按全部有效点位重建 `user_route_regions`。
- 起点命中当前城市时返回 `region_match=start`。
- 仅途经点或终点命中时返回 `region_match=through`。
- 编辑路线任何点位后，必须重新生成地区覆盖表，不允许保留旧覆盖数据。

### 5.4 官方路线归属

- 管理后台地图选点若无法直接获得城市信息，则要求运营人员确认每个点位所属城市。
- 后端继续验证城市代码是否属于新疆支持目录。
- 官方路线主城市取起点，覆盖城市由全部点位生成。
- 已发布官方路线不得因客户端升级丢失现有地区信息。

### 5.5 关联路线发起同行

- 从官方路线或骑友路线发起同行时，点位及地区必须由后端读取已保存路线数据。
- 不信任小程序再次提交的路线点位地区。
- 集合点默认取路线起点，主城市同步为路线起点城市。
- 用户后续手动修改集合点、途经点或终点时，修改后的点位重新走 `choosePoi + 地区确认` 流程，并标记快照已自定义。

## 6. 城市名称标准化设计

### 6.1 映射原则

前后端共享同一版本的新疆行政区划目录。数据库和接口只使用标准代码，名称仅用于展示和匹配。

示例：

| `choosePoi.city` 可能值 | 标准名称 | `city_code` |
| --- | --- | --- |
| 乌鲁木齐、乌鲁木齐市 | 乌鲁木齐市 | `650100` |
| 克拉玛依、克拉玛依市 | 克拉玛依市 | `650200` |
| 昌吉、昌吉州、昌吉回族自治州 | 昌吉回族自治州 | `652300` |
| 博州、博尔塔拉、博尔塔拉蒙古自治州 | 博尔塔拉蒙古自治州 | `652700` |
| 巴州、巴音郭楞、巴音郭楞蒙古自治州 | 巴音郭楞蒙古自治州 | `652800` |
| 克州、克孜勒苏、克孜勒苏柯尔克孜自治州 | 克孜勒苏柯尔克孜自治州 | `653000` |
| 伊犁、伊犁州、伊犁哈萨克自治州 | 伊犁哈萨克自治州 | `654000` |

实际别名清单必须覆盖项目支持的全部新疆地州/市，并由测试锁定。

### 6.2 归一化顺序

1. 去除首尾空白、连续空格。
2. 统一常见标点和全半角字符。
3. 先按标准全称精确匹配。
4. 再按受控别名表匹配。
5. 禁止使用包含关系模糊匹配，例如不能仅凭“州”“市”猜测。
6. 未匹配时弹出人工确认，不默认使用全局当前城市。

### 6.3 数据版本

- 前端目录版本与后端目录版本均设置 `region_data_version`。
- 提交时可附带客户端目录版本，用于日志分析，不作为业务主键。
- 后端目录为最终代码合法性校验依据。
- 行政区划目录更新必须同步更新别名测试和旧名称兼容表。

## 7. 小程序前端改造

### 7.1 公共选点能力

新增统一工具或组件，例如：

```text
frontend/src/utils/poi-location.ts
frontend/src/components/region-confirm-sheet/
```

建议接口：

```ts
interface RegionPoiPoint {
  name: string;
  address?: string;
  latitude: number;
  longitude: number;
  province_code: "650000";
  city_code: string;
  city_name: string;
  district_code?: string;
  district_name?: string;
  region_source: "choose_poi" | "manual";
}

async function chooseRegionPoi(options?: {
  initialRegion?: SelectedRegion;
  requireDistrict?: boolean;
}): Promise<RegionPoiPoint | null>;
```

处理规则：

- 用户取消选点返回 `null`，不显示“失败”提示。
- `type !== 2` 时提示“请选择具体地点”，不保存城市中心作为集合点。
- 城市匹配成功后展示所属城市，允许用户修改。
- 城市匹配失败时必须打开城市选择器。
- 区县选择器只展示当前城市的下属区县，避免非法父子关系。
- 所属地区与 POI 名称、地址、坐标一起保存在表单状态中。

### 7.2 发起同行页面

替换集合点、途经点、终点的 `chooseLocation`：

- 集合点卡片显示地点名称和所属城市/区县。
- 途经点列表每项显示地区简写。
- 终点显示所属地区。
- 关联路线导入点位时使用路线已有地区，不再次弹出确认。
- 不再将全局 `selectedRegion` 无条件写入每一个地图点位。
- 提交前检查所有点位必须有 `city_code`；区县按产品配置决定是否必填。

### 7.3 录入路线页面

- 起点、途经点、终点统一调用公共选点能力。
- 起点必须有城市代码，否则不能保存。
- 跨城市路线允许每个点位使用不同 `city_code`。
- 编辑旧路线时，已有点位地区正常回显；缺失地区的点位在保存前要求用户补充。
- “公开路线”确认弹窗继续提示点位将公开，并增加“路线可能出现在途经城市列表中”的说明。

### 7.4 城市/地区筛选页面

- 全局城市选择仍只决定用户正在浏览哪个地区，不用于覆盖新点位真实城市。
- 用户切换城市后同行、官方路线和骑友路线同步刷新。
- 区县筛选开启时，对 `district_code=null` 的内容不错误归入任一区县。
- 可提供“全市”选项，查询只传 `city_code`。

## 8. 后端改造

### 8.1 DTO 校验

同行、用户路线和后台官方路线点位 DTO 统一校验：

- `province_code` 固定或归一为 `650000`。
- `city_code` 必填，必须存在于新疆地市目录。
- `district_code` 可选；存在时必须属于对应 `city_code`。
- 经纬度必须是有效 GCJ-02 数值范围，并处于项目支持的大致地理边界内。
- 名称和地址执行长度限制及文本清理。
- 客户端传来的 `city_name/district_name` 仅用于日志或展示，不用于数据库过滤条件。

### 8.2 地区解析策略调整

地区归属不再调用 `MapProviderService.enrich`。实施时应移除创建、编辑、历史回填链路中的逆地址解析分支，并删除仅服务于地区识别的 Key 配置读取和策略配置。

```text
新客户端 + choosePoi 返回可识别城市
  → 标准化映射 city_code
  → 页面展示并允许用户修改
  → 服务端校验行政区目录后保存

choosePoi 城市为空或无法识别
  → 强制打开人工城市确认
  → 用户确认后提交标准 city_code

旧客户端缺少 city_code
  → 返回“请升级后重新选择地点”或要求补充城市

后台批量导入/历史缺失数据
  → 使用已有合法 city_code、结构化导入字段或管理后台人工修复
  → 无法确认的记录保持待处理，不猜测城市
```

地区归属采用固定业务规则，不新增解析策略环境变量，也不保留可恢复在线逆地址解析的模式开关：

- 地区只允许来自 `choosePoi` 城市映射、人工确认，以及这两类来源形成的已保存点位快照。
- 新建和修改点位必须提交合法地市代码，作为服务端校验规则，不提供关闭必填校验的配置。
- 删除地区链路使用的 `TENCENT_MAP_KEY`、`TENCENT_MAP_SECRET` 和 `REGION_VERIFY_SAMPLE_RATE` 等配置及读取逻辑，而非保留为空。
- 若项目其他独立功能仍存在地图服务配置，地区模块不得读取或调用；相关功能是否保留应单独评审，不作为本方案兜底。

#### 8.2.1 配置与依赖删除清单

本节为待实施/核验要求，不代表已删除生产环境配置。

| 对象 | 修改要求 | 验证方式 |
| --- | --- | --- |
| 地区逆地址解析 Key 与签名配置 | 删除地区链路使用的 `TENCENT_MAP_KEY`、配套 Secret 及配置读取；不得仅将值置空 | 地区代码中不存在这些配置读取 |
| 环境模板与部署注入 | 从环境变量示例、Compose、初始化脚本及部署说明中移除上述地区配置；实际环境清理须按部署流程执行 | 新部署无需填写地区地图 Key |
| 逆地址解析策略 | 删除自动回退、抽样复核、重试、缓存和配额配置，包括 `REGION_VERIFY_SAMPLE_RATE` | 不存在切换回逆地址解析的运行分支 |
| 在线历史数据修复 | 删除依赖逆地址 API 的回填任务和调用 | 缺失城市进入人工待处理报告 |
| 测试与监控 | 删除对逆地址服务成功响应的依赖，增加无 Key、禁止外部地区请求的回归断言 | 创建、编辑、筛选无需逆地址网络请求即可完成 |

原建议中的 `REGION_RESOLUTION_MODE`、`REGION_REQUIRE_CITY_CODE` 不再作为本次新增配置要求；若实现中已引入，应收敛为上述固定规则。不得提供 `map`、`hybrid` 或其他在线逆地址模式。

删除范围限定为**地区归属识别技术**：微信原生选点、地图展示和逐点“查看地图”保持可用。既有独立道路规划或后台地图展示配置不能被地区模块复用，也不在本次文档修订中授权删除其功能。

### 8.3 同行保存

- 主表城市取集合点 `city_code`，不再单独取页面全局城市。
- 途经点和终点逐点保存地区代码。
- 关联路线时，地区来源为服务端路线记录。
- 编辑点位或再次发起时重新计算主归属和点位覆盖。
- Redis GEO Key 使用最终集合点城市：`geo:rides:{city_code}`。
- 主城市变化时先移除旧 GEO Key，再写入新 GEO Key。

### 8.4 路线保存与覆盖表

- 用户路线主表城市取起点点位。
- `user_route_points` 保存每个点位地区。
- 保存和编辑均先删除旧覆盖行，再按点位去重生成 `user_route_regions`。
- 官方路线使用相同原则生成 `route_regions`。
- 覆盖表唯一键继续使用 `(资源ID, city_code, district_code)`。
- 对区县未知的点位使用空字符串作为覆盖表区县值，但不得匹配某个具体区县。

### 8.5 服务端可信边界

仅依赖 `choosePoi.city` 时，服务端只能确认代码是否合法，不能从密码学或空间关系上证明坐标确实属于该城市。因此必须明确：

- 这是产品数据质量风险，不是身份鉴权风险。
- 普通用户不能通过错误城市获得额外私密数据，但可能使公开内容出现在错误城市。
- 保留举报、后台人工修正和异常监控。
- 若后续出现明显滥用，可升级为不依赖在线 Key 的离线行政区边界点落区校验；不恢复腾讯逆地址解析兜底。

## 10. 数据库方案

### 10.1 本次必需变更

本次核心改造不要求新增重复的“所属城市”字段，因为现有结构已经覆盖：

- `rides.city_code/district_code`
- `ride_points.city_code/district_code`
- `routes.city_code/district_code`
- `route_points` 与 `route_regions`
- `user_routes.city_code/district_code`
- `user_route_points` 与 `user_route_regions`

主要工作是改变字段写入来源、补齐终点地区、修复错误兜底逻辑和重建覆盖索引。

### 10.2 可选增强字段

若后续需要追踪地区数据质量，可在单独迁移中增加：

```text
region_source: choose_poi | manual | route_snapshot | backfill
region_verified_at: datetime nullable
region_data_version: integer nullable
```

不建议为本次上线强制增加这些字段，以免扩大迁移范围；首期可通过结构化日志和埋点观察。

### 10.3 历史数据

- 已有合法 `city_code` 的记录保持不变。
- 已有地区覆盖表继续使用。
- 缺少城市代码的数据不默认归为乌鲁木齐。
- 缺失数据仅通过已有合法地区字段、结构化导入信息、用户重新编辑或后台人工修复处理。
- 回填脚本必须支持 dry-run、幂等、失败报告和断点续跑。
- 无确定地区来源的历史记录保持待处理，不通过地址文本或当前默认城市猜测。

## 11. 查询与排序规则

### 11.1 同行

```text
WHERE
  ride.city_code = selectedCity
  OR ride.points.some(city_code = selectedCity)
```

选择区县时增加 `district_code` 条件。排序：

1. 集合点命中当前地区。
2. 途经点或终点命中当前地区。
3. 已取得定位时，按集合地点距离由近至远。
4. 无定位时，按发布时间倒序。
5. 相同时间以 ID 倒序保证稳定分页。

### 11.2 路线

```text
WHERE
  route.city_code = selectedCity
  OR route.regions.some(city_code = selectedCity)
```

排序：起点命中优先，仅覆盖地区命中次之，再按运营权重/发布时间等现有规则排序。

实施补充（2026-09-03）：

- 优先级必须在分页前生效，不得只对当前页重新排序。
- 官方路线游标增加分组信息；骑友公开路线使用带 `rp1.` 前缀的时间/ID/分组游标，仍接收旧数字游标。客户端应将 `nextCursor` 视为不透明字符串，不自行解析或转成数字。
- 城市、区县、来源或其他筛选变更后从第一页重新加载，不复用旧游标。
- 路线首页跨来源顺序为“本地起点官方→本地起点骑友→仅途经官方→仅途经骑友”；每组内沿用对应接口的稳定排序。通过分组分页继续加载全部匹配内容，不截断为各来源前50条。
- 官方列表缓存增加排序版本，避免继续读取旧页内排序结果。

## 16. 发布与灰度

### 16.1 功能开关

建议增加：

- `poi_region_client_primary`：是否启用 `choosePoi` 城市主导。
- `poi_region_manual_confirm`：是否显示人工地区确认。
- 不设置逆地址解析、Key 或抽样复核开关。

以上开关只能控制界面灰度，不能改变城市必填规则。城市缺失且人工确认入口不可用时，必须阻止提交并提示重试或升级；不得自动使用当前浏览城市，也不得转为逆地址解析。

### 16.2 灰度顺序

1. 测试环境启用，完成新疆主要城市真机抽样和人工确认兜底测试。
2. 生产后端先兼容新旧 DTO，但关闭并删除地区逆地址解析调用。
3. 发布小程序体验版，开启人工确认和埋点。
4. 小比例启用客户端城市主导。
5. 观察 24～72 小时自动识别率、人工修改率、失败率和错城反馈。
6. 扩大至全量，持续保留人工修正入口和监控。

### 16.3 发布门禁

- 主要新疆地州/市别名映射测试全部通过。
- `choosePoi.city` 真机返回率达到评审阈值。
- 无法识别城市时不会静默写入当前浏览城市。
- 跨城市同行和路线覆盖查询正确。
- 历史公开内容数量与升级前对账，无异常大幅减少。
- API TP99 不因地区校验超过现有列表与详情指标。

## 17. 回滚方案

- 关闭 `poi_region_client_primary` 后，只能切换到“选点 + 强制人工城市确认”的兼容流程；不得恢复旧版静默填入当前浏览城市的逻辑。
- 后端继续兼容已提交的标准 `city_code`，不需要回滚已写数据。
- 若发现城市归类错误，暂停新内容公开展示并运行地区修复脚本。
- 覆盖表可按点位重新生成，不直接手工删除主业务记录。
- 回滚时也不恢复腾讯地图逆地址解析；无法识别城市的点位统一进入人工确认流程。
- 回滚不得把无法识别数据统一写为乌鲁木齐。

## 18. 风险清单

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 微信端部分版本不返回 `city` | 无法自动归属 | 人工城市确认兜底，真机兼容测试 |
| 城市名称存在简称 | 映射失败 | 受控别名表和监控，不使用模糊猜测 |
| 客户端伪造城市代码 | 内容错城展示 | 后端白名单、用户确认、举报与后台人工修正 |
| 区县无法自动识别 | 区县筛选漏数 | 区县人工确认；首期以城市级为主 |
| 旧数据缺少地区 | 列表漏数 | 回填、人工修复、失败隔离 |
| 跨城点位只保存主城市 | 途经城市无法发现 | 必须逐点保存并重建覆盖表 |
| 地区目录版本不一致 | 合法代码被拒绝 | 目录版本管理、兼容旧代码 |
| 不使用逆地址 API | 服务端无法自动证明坐标所属城市 | 明确信任边界、强制用户确认、后台纠错；必要时后续采用离线行政区边界校验 |

## 19. 验收标准

满足以下条件后方可认定改造完成：

1. 新建同行、骑友路线的地图选点统一使用公共 `choosePoi` 流程。
2. 地市信息可自动映射；映射失败时必须人工确认，不得静默沿用浏览城市。
3. 同行集合点和路线起点正确写入主城市字段。
4. 所有途经点、终点保存各自城市信息。
5. 跨城市内容可在相关城市列表出现，并正确区分“本地起点/集合点”和“途经本地”。
6. 删除腾讯地图逆地址 Key 及相关地区配置后，新建内容仍可完成城市级保存与筛选。
   - 不只是“未配置 Key 时能工作”：环境模板、部署注入和地区服务调用均需清理；自动确认、人工确认、关联路线、历史修复及回滚路径均不得请求逆地址 API。
7. 区县未知时不错误归入任一区县。
8. 非法或不支持的地区代码被服务端拒绝。
9. 旧数据、旧客户端和关联路线流程不发生破坏性回归。
10. 前后端单元测试、接口测试、小程序生产构建和真机验收全部通过。

实施前需要最终确认：

1. V2.3.0 是否以地州/市级筛选为 P0，区县精确筛选降为 P1。

6. 是否在本次同步补齐用户路线终点 `end_point` 结构；本方案建议同步完成，避免终点覆盖城市长期缺失。
