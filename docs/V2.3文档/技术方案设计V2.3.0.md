# 摩搭子助手 V2.3.0 技术方案设计

## 1. 现状基线

- 官方路线已有 `RoutePoint`、`Route.polyline`，小程序官方路线详情已使用地图折线；后台仍通过文本输入折线 JSON 和逐行填写点位。
- 用户路线使用 `UserRoute` 的起终点字段与 `waypoints` JSON，详情页只有 markers，没有 polyline、行政区划和第三方路线链接。
- 同行使用 `Ride.meetup_*`、目的地文本和 `RouteRideLink`，没有途经点、终点坐标与发布快照。
- 首页和同行创建页分别写死乌鲁木齐 `650100`；路线页要求用户输入城市码。
- 首次资料页允许跳过；微信号可为空且数据库无唯一索引。
- 管理后台路线模块只管理官方 `routes`，缺少面向 `user_routes` 的查询、详情和治理接口。

V2.3.0 采用增量兼容方案，保留既有字段供旧数据和旧客户端读取，新增标准点位、地区索引和快照结构。

## 2. 总体架构

```text
小程序/管理后台
  ├─ 地图选点与排序
  ├─ 城市选择与分享
  └─ 资料完整度守卫
        ↓ /api/v1
NestJS
  ├─ Route / UserRoute / Ride
  ├─ AdminUserRoute 用户路线治理与审计
  ├─ Region 行政区划目录、城市名称映射与人工确认
  ├─ MapProvider 道路规划适配器
  ├─ ShareMetadata 分享元数据
  └─ ProfileCompletenessGuard
        ↓
MySQL（点位、快照、地区索引） + Redis（地图结果/地区缓存）
        ↓
腾讯位置服务或经确认的地图服务 + COS
```

地图服务通过 `MapProvider` 接口隔离道路规划等独立能力。地区归属不调用 `reverseGeocode`，不配置腾讯地图 Key 兜底；新客户端使用 `wx.choosePoi.city` 映射和人工确认取得标准地区代码。

## 3. 路线方案

### 3.1 点位与折线

官方路线继续使用 `RoutePoint` 和 `Route.polyline`。用户路线新增 `UserRoutePoint` 与 `UserRoute.polyline`，迁移后 `waypoints` JSON 暂时保留一个版本周期作为兼容读字段，服务端写入时以点位表为准并同步兼容 JSON。

点位发生变化时：

1. 前端提交有序点位，不提交可信折线。
2. 后端校验一个 start、最多一个 end、顺序连续和坐标范围。
3. 调用道路规划服务逐段规划，合并相邻段并去除重复端点。
4. 抽稀至最多 500 点，保存 `polyline`、`polyline_status`、`polyline_provider` 和更新时间。
5. 服务失败时保存点位并标记 `pending/failed`；异步任务可重试，不伪造道路轨迹。

官方路线后台可在发布前要求 `polyline_status=ready`；用户私密路线允许无折线，公开路线至少有起点，详情按状态降级。

### 3.2 第三方路线链接

新增 provider、URL、校验状态。后端执行：

- 仅 HTTPS；最大 1000 字符；拒绝用户名密码、内网 IP、localhost 和非白名单域名。
- 解析重定向后的最终域名由后端异步完成，禁止服务端无限重定向。
- 返回前不拼接用户隐私参数；日志只记录 provider、域名和哈希，不记录完整查询串。
- 白名单从环境配置读取，例如 `ROUTE_EXTERNAL_URL_ALLOWLIST`。

### 3.3 导航

- 单点导航：客户端调用 `Taro.openLocation` 打开起点、集合点或终点。
- 完整路线：存在已验证第三方链接时，通过受支持方式打开；若微信限制外部跳转，则复制链接并给出提示。
- 不将点位折线直接作为逐向导航指令，不申请后台持续定位。

## 4. 同行方案

### 4.1 点位和快照

新增 `RidePoint`，类型为 `waypoint` 或 `destination`；集合点继续保存在 `Ride.meetup_*` 以兼容当前查询和距离排序。新增同行 `route_snapshot` JSON 保存：来源类型/ID、标题、起终点、点位、抽稀折线、距离、时长及快照版本。

创建流程：

- 未关联路线：客户端通过 `wx.choosePoi` 和人工确认提交集合点、途经点、终点及标准地区代码；后端校验行政区目录并生成覆盖索引。
- 关联路线：后端按 route ID 读取当前可见路线，服务端生成快照；不信任客户端提交的路线点位。
- 用户可修改集合点；如果编辑已导入的途经/终点，快照标记 `customized=true`。

详情优先读取 `RidePoint + route_snapshot`，旧同行无新字段时仍返回现有目的地文本。

### 4.2 再次发起

新增只读模板接口，不直接创建记录。服务端确认当前用户是原发起人或有效历史参与者，返回允许复制的字段。前端将模板装载到创建页，清空时间并要求用户确认；最终仍调用现有 `POST /rides`。

这样避免用户点击“再次发起”就生成垃圾草稿，也复用现有安全协议和幂等逻辑。

## 5. 城市/地区方案

> 2026-09-02 增量决策：新建内容的地市来源调整为 `wx.choosePoi.city` 标准化映射，人工确认兜底；删除腾讯地图 Key 逆地址解析配置，不将其用于兼容、校验或历史回填。实施细节和可信边界以《[`wx.choosePoi` 城市归属与筛选改造方案](./wx.choosePoi城市归属与筛选改造方案V2.3.0.md)》为准。

### 5.1 数据源

维护版本化的新疆行政区划静态数据：省级 `650000`、地州/市和区县。发布时固化一份 JSON 到前端用于选择，后端维护同版本表或常量用于校验。行政区划更新必须带 `region_data_version`。

点位选定后由 `wx.choosePoi.city` 映射地市，无法识别时由用户人工确认。后端保存并校验 `province_code/city_code/district_code`；标准代码用于过滤，城市名称只用于映射和展示。

### 5.2 路线覆盖索引

为官方路线和用户路线分别建立地区覆盖表，按所有点位去重写入。主列表查询使用起点 `city_code/district_code` 的普通索引；“途经本地”查询使用覆盖表，避免对 JSON 扫描。

同行和路线列表默认使用主归属字段与覆盖表做 `OR` 过滤；以集合点/起点命中的内容优先排序，只有覆盖表命中的内容返回 `region_match=through` 并展示“途经本地”。

### 5.3 客户端状态

新增 Zustand 城市状态：`selectedRegion`、`source=manual|location|default`、`updatedAt`。优先级为用户手选 > 合法定位推荐 > 默认乌鲁木齐。城市选择持久化，不因下一次定位自动改变。

## 6. 分享方案

官方路线、用户路线、同行详情统一提供分享元数据函数，输出 `title/path/imageUrl`。页面注册 `useShareAppMessage`，并在需要时调用 `Taro.showShareMenu`。

- 分享 path 只包含资源 ID 和可选的非敏感来源参数。
- 用户私密路线不开放分享；登录后仍由服务端鉴权。
- 分享图片优先使用路线封面；无封面使用受控 COS 品牌图。
- 同行标题由服务端返回标准化摘要，避免各端规则不一致。
- 详情不存在、已取消或下线时显示可理解状态，不跳首页制造误解。

## 7. 资料完整度方案

后端计算 `profile_complete` 与 `missing_profile_fields`，不能只依靠前端判断。新增业务守卫应用于：创建同行、报名同行、将用户路线设为公开。更新资料时对微信号标准化后执行唯一校验。

前端统一 `ensureProfileComplete(intent)`：若不完整，保存目标操作和返回地址，进入资料页；保存成功后只恢复一次，防止循环提交。首次登录不再显示“跳过后进入关键操作”的误导，但普通浏览仍可进入。

微信号是用户声明信息，页面和隐私政策不得表述为“微信已认证”。

## 8. 管理后台地图编辑器

新增可复用 `RouteMapEditor`：

- 搜索/地图选点；添加起点、途经点、终点。
- 拖拽或上下按钮调整顺序；删除点位；自动编号。
- 预览道路折线、里程和预计时长；失败时显示重试。
- 城市由选点结果映射，无法识别时运营人员必须从受控行政区目录确认；区县可人工选择，不能填写目录外代码。
- 保留“高级 JSON 查看”只读模式用于排障，不作为正常录入入口。

### 8.1 用户发布路线治理

用户路线治理与官方路线编辑采用独立接口和页面区域，避免复用官方路线 DTO 造成字段混淆或意外改写用户内容。

- `AdminUserRouteService` 提供分页查询、详情、下架和恢复；查询关联发布者、标准点位、地区覆盖、收藏/评论/同行关联计数。
- 下架使用条件更新，仅允许 `status=1` 的路线进入管理员下架状态，同时写入 `offlined_at`、`offline_reason`、`offlined_by`。
- 恢复仅允许超级管理员操作，且必须同时满足 `status=2` 与 `offlined_at IS NOT NULL`；因此用户自行删除的数据不能被后台恢复。
- 下架和恢复与后台操作日志处于同一事务，保证治理结果和审计记录一致。
- 管理后台只展示详情和治理动作，不提供编辑用户标题、说明、点位、图片或可见性的入口。

## 9. 数据迁移与兼容

迁移分四步：

1. 只新增 nullable 字段和新表，部署兼容后端。
2. 使用已有合法地区字段或管理后台人工确认补齐官方 `RoutePoint`；把用户路线起点/途经/终点转换为 `UserRoutePoint`，生成地区索引。
3. 对可规划路线分批生成 polyline；失败记录原因，不阻塞发布。
4. 新端稳定一个版本周期后停止写旧 `waypoints` JSON，删除旧字段另立版本审批。

用户路线治理字段作为 nullable 增量字段上线，不改变既有用户路线读取；新增 `(status, offlined_at, id)` 索引支持后台状态分页和恢复条件判断。

旧同行只展示集合点和目的地文本；旧路线无地区码时通过现有 city_code 或离线回填，未完成回填的内容不应错误出现在其他城市。

## 10. 缓存、限流与性能

- 道路规划缓存键由有序坐标（按 5～6 位小数归一化）和 provider 版本生成，TTL 7 天。
- 地区识别不设置逆地址缓存、Key、配额或在线回填任务；人工修复需记录操作者和变更前后代码。
- 列表只查询摘要，不返回 polyline；详情才返回抽稀折线。
- 地区过滤字段和覆盖表必须建立组合索引并通过 `EXPLAIN` 验证。

## 11. 安全与隐私

- 第三方链接做 SSRF 防护和域名白名单；客户端不得直接信任数据库 URL。
- 分享卡不显示微信号、精确联系方式和隐私路线。
- 地图坐标属于位置数据，沿用按场景授权和最小化收集原则；隐私政策补充用途、保存范围和删除方式。
- 微信号唯一冲突返回通用提示，不暴露占用者。
- 用户路线下架/恢复按后台角色授权，理由必填，并记录不可抵赖的操作日志；管理端响应不返回用户敏感联系方式。

## 12. 监控与回滚

监控：`choosePoi` 城市返回率、城市映射失败率、人工修改率、后台纠错率、地图规划成功率、分享打开成功率、城市空列表率、资料拦截完成率、再次发起成功率。

通过 feature flags 分别控制：`route_polyline_v23`、`external_route_link_v23`、`ride_points_v23`、`region_switch_v23`、`profile_gate_v23`。出现问题时关闭前端入口；新增字段保持兼容，数据库不执行破坏性回滚。
