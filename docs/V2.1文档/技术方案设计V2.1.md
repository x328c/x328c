# 摩搭子助手 V2.1 技术方案设计

> 状态：Draft 1.0
> 原则：兼容新增、增量迁移、服务端判定、审核优先、默认安全关闭

## 1. 真实基线与兼容策略

当前技术栈保持不变：后端 NestJS 10 + Prisma 5 + MySQL 8 + Redis 7；小程序 Taro 4.2 + React 18 + Zustand；管理后台 React 19 + Vite 8 + Ant Design 6。

代码基线：

- `RouteRideLink` 已存在，且 `route_id + ride_id` 唯一；可扩展用于用户选路线创建同行；
- `Activity` 当前只有 `route_description` 文本，没有路线外键关系；
- `Ride`、`Activity` 均保留集合地点等业务快照字段；
- 路线已有发布/下架、收藏、缓存和 `route.enabled`；
- 论坛已有审核、举报、限流、幂等、软删除和人工队列能力，路线评论应复用其安全模式但不强耦合论坛开关；
- 法规模块已有修订、来源和复核工作流，可借鉴但不把事故指南伪装成法规原文；
- 现有发起同行页面仅前端保存 `agreed` 布尔值，服务端无法证明用户确认了哪个版本；活动及两类报名链路缺少同等确认；
- 设置页四个入口目前均为占位 Toast。

用户侧名称迁移仅修改展示层资源和事件字典。`Ride`、`Regulation`、数据库表、API、错误码对象名继续保留，避免破坏 V1 客户端、管理后台、监控和历史数据。

## 2. 模块设计

### 2.1 路线与同行/活动联动

#### 数据关系

继续使用 `RouteRideLink` 连接路线与同行，并新增 `RouteActivityLink`：

| 字段 | 类型/约束 | 说明 |
|---|---|---|
| id | BigInt PK | 自增主键 |
| route_id | BigInt FK | `Route`，删除策略 `Cascade` 仅适用于路线物理删除；生产业务只软删除 |
| activity_id | BigInt FK | `Activity` |
| source | VarChar(32) | `route_detail`、`create_form`、`admin_manual` |
| created_at | DateTime | 服务端时间 |

约束：`@@unique([route_id, activity_id])`、`@@index([activity_id])`。

`Ride`/`Activity` 继续保存集合地址、坐标、目的地或路线描述作为创建时快照。路线标题、点位和状态由关系查询获取，不能只依赖客户端复制值。路线后续更新不静默覆盖已发布业务的集合信息；路线下架只阻止新绑定，并在既有详情显示“所选路线已下架”。

#### 创建校验

创建 DTO 增加可选 `route_id` 和 `route_link_source`，服务端必须：

1. 校验登录、用户状态、写入限流和幂等键；
2. 校验 `route.link_enabled` 与 `route.enabled`；
3. 查询路线 `status=PUBLISHED AND deleted_at IS NULL`；
4. 校验城市一致性；不一致时返回可识别错误，不自动改城市；
5. 校验预填坐标仍在允许范围，最终业务字段按 DTO 规则校验；
6. 在同一数据库事务中创建业务记录、关系、发起人参与记录和协议确认；
7. 写后清理路线详情、关联同行/活动及业务详情缓存。

更新已发布同行/活动时，V2.1 默认不允许更换路线；发起人需取消后重建。若产品必须支持修改，应作为后续独立需求并重新确认参与人和安全协议。

### 2.2 路线评论

新增 `RouteComment`。首版为纯文字一级评论，V2.1 增量支持每条评论最多 2 张图片：

| 字段 | 说明 |
|---|---|
| id、route_id、user_id | 主键及关系 |
| content | 2-500 字，服务端清洗后的纯文本 |
| images | JSON 图片 URL 数组，最多 2 项；仅接受当前用户上传至 `route-comments/` 并完成回调登记的图片 |
| content_hash | 用于重复提交识别，不用于公开 |
| status | 保留兼容字段，新评论固定为 `1=NORMAL`；删除通过 `deleted_at` 表示 |
| report_count、reported_at | 不同用户举报次数和最近举报时间 |
| moderation_status | 兼容历史数据，新评论固定为已通过，不参与业务判断 |
| moderation_attempts、next_retry_at | 仅为兼容历史字段，不再执行自动重试 |
| rejection_reason、offline_reason | 兼容历史数据/管理员删除原因 |
| published_at、created_at、updated_at、deleted_at | 生命周期 |

建议约束与索引：

- `@@index([route_id, status, published_at, id])`；
- `@@index([user_id, deleted_at, created_at, id])`；
- 重复提交由 `Idempotency-Key` 强约束，`content_hash` 仅用于风险提示，不能阻止用户合法重复表达。

公开条件必须同时满足：路线已发布且未删除、评论状态为 `NORMAL`、`published_at` 非空、`deleted_at` 为空、读开关开启。举报只累计次数，不改变评论可见性；管理员核实后执行软删除并记录原因与审计日志。

### 2.3 用户录入路线

新增 `UserRoute` 与 `UserRouteFavorite`。用户路线与运营维护的官方 `Route` 分表，避免审核状态、发布流程和来源责任混用。`visibility=1` 时所有详情读取均校验创建者；`visibility=2` 且 `status=1` 时进入路线广场，支持关键词、难度、里程和游标分页。删除仅将 `status` 置为 2。

起点为必填，终点名称与经纬度必须成组出现；途经点最多 20 个，路线图片最多 6 张且必须来自当前用户 `user-routes/` 上传目录。公开详情的评论复用 `RouteComment`，通过可空 `user_route_id` 关联并沿用图片、举报和后台删除规则。用户路线的列表卡片和详情页与系统路线统一展示封面、起终点、里程、时长、难度、地图点位、路线说明和安全提示。

附近功能的设备位置继续模糊处理；用户主动地图选点创建的路线坐标是路线内容，为地图复现必须精确保存。前端在公开前明确提示点位会公开，避免选择住址等敏感地点。

发布模式为“提交即发布 + 用户举报 + 后台删除”。评论不调用第三方内容审核，不设置待复审状态。图片上传限定为 jpg/png/webp、5MB 以内，上传回调校验文件头、尺寸、用户目录和 COS 地址。同一用户对同一评论只能举报一次，举报创建和计数递增位于同一事务；举报次数仅供后台排序参考。管理员删除必须填写原因并写 `operation_logs`。

### 2.3 骑行应急知识

事故指南是“官方文件的运营摘要”，不是法规原文。新增版本化模型，避免把摘要写入 `RegulationRevision.content`：

`SafetyGuideArticle`：`code`（唯一，首条为 `accident_handling`）、标题、摘要、状态、当前修订 ID、发布时间、下架原因、创建/更新时间。

`SafetyGuideRevision`：文章 ID、版本、结构化 `content_json`、来源标题、来源 URL、来源机关、来源发布日期/施行日期、内容说明、创建人、复核人、复核/发布时间、内容哈希、最后复核时间。

规则：

- 创建人与复核人不能相同；发布形成不可变修订；
- 发布前校验来源 URL、版本、复核时间和所有必需区块；
- 发布、修订、失效、下架写管理员审计日志；
- 前台响应带 `version`、`contentHash`、`lastVerifiedAt` 和来源字段；
- 内容过复核期显示提醒；来源链接失败不隐藏来源；
- `safety_guide.enabled=false` 时返回兼容功能关闭错误，不影响原法规检索、路线或同行。

首版可由迁移后的种子脚本导入[骑行应急知识内容稿](./事故处理指南内容稿.md)，但种子数据只能生成草稿，必须由另一管理员复核发布。

### 2.4 安全须知版本与确认凭证

不要把协议仅保存在前端常量或 `agreed=true`。新增：

`SafetyAgreement`：协议代码、版本、标题、正文、内容哈希、适用场景、状态、发布/失效时间、创建人、复核人、最后法律复核时间。

适用场景固定为：`ride_create`、`ride_join`、`activity_create`、`activity_register`。同一场景同一时间只能有一个有效版本。

`SafetyAgreementAcceptance`：用户 ID、协议 ID、场景、目标类型、目标 ID、确认时间、内容哈希、request ID、幂等键。目标 ID 必须指向本次创建或报名对象；不保存 token、openid、手机号、精确位置、设备指纹或协议全文。

写接口请求新增：

```json
{
  "agreement": {
    "id": "12",
    "version": "2026.08.1",
    "content_hash": "sha256:..."
  }
}
```

服务端在业务事务内验证当前有效版本和哈希，然后同时写业务记录与接受凭证。客户端缺失、版本过期、哈希不符或场景不符均返回兼容错误响应，例如业务码 `56001 AGREEMENT_REQUIRED`、`56002 AGREEMENT_VERSION_EXPIRED`，HTTP 状态按现有异常规范使用 409/422。旧客户端在强制开关开启前仍可使用；强制开启必须满足最低支持版本门禁，避免无提示阻断存量客户端。

确认记录是风险告知证据，不代表免责。协议发布必须双人复核；新版本发布后仅影响新动作，不追溯修改历史确认。

### 2.5 设置

新增 `UserSetting`（`user_id` 唯一）保存应用内偏好：个人资料公开范围、联系方式展示、同行/活动/系统通知偏好及更新时间。系统权限状态只由小程序运行时读取，不写成服务端授权事实。

新增 `AppFeedback` 保存意见反馈：用户 ID 可空、类型、描述、可选文件记录 ID、状态、处理人、处理摘要及时间。描述和图片按 UGC 规则审核；日志不记录正文。

清理缓存只删除小程序非关键缓存，保留 token、登录回跳、待提交草稿和幂等状态。账号注销若进入 P1，必须单独设计身份复核、未完成活动校验、冷静期、撤回、数据保留和匿名化，不在设置页直接物理删除用户。

## 3. API 设计

兼容新增继续使用 `/api/v1`：

| 方法与路径 | 权限 | 说明 |
|---|---|---|
| `POST /api/v1/rides` | 登录 | DTO 可选 `route_id`，并提交协议版本 |
| `POST /api/v1/activities` | 登录 | DTO 可选 `route_id`，并提交协议版本 |
| `POST /api/v1/rides/:id/join` | 登录 | 提交同行报名协议版本 |
| `POST /api/v1/activities/:id/register` | 登录 | 提交活动报名协议版本 |
| `GET /api/v1/routes/:id/comments` | 公开 | 稳定游标，仅公开评论 |
| `POST /api/v1/routes/:id/comments` | 登录 | 创建并立即发布评论，要求幂等键 |
| `PUT /api/v1/route-comments/:id` | 登录 | 修改本人未屏蔽评论 |
| `POST /api/v1/reports` | 登录 | 举报路线评论；同一用户和评论幂等 |
| `DELETE /api/v1/route-comments/:id` | 登录 | 删除本人评论，幂等 |
| `GET /api/v1/route-comments/mine` | 登录 | 本人评论与审核状态 |
| `GET /api/v1/safety-guides/accident-handling` | 公开 | 当前发布版本及来源 |
| `GET /api/v1/safety-agreements/active` | 登录 | 按场景获取当前版本 |
| `GET/PUT /api/v1/users/me/settings` | 登录 | 读取/更新应用内设置 |
| `POST /api/v1/feedback` | 可选登录 | 提交意见反馈，限流/幂等 |

管理端新增评论审核、指南修订和协议版本接口，沿用管理员角色守卫、操作原因、request ID 和 `operation_logs`。静态路由（如 `mine`、`active`、`accident-handling`）必须注册在 `:id` 之前，并加入路由顺序自动化测试。

列表统一返回 `items`、`nextCursor`、`hasMore`；无效游标返回现有兼容错误结构并带 `requestId`。评论正文和设置值不得进入请求日志。

## 4. 缓存、一致性和任务

Redis Key 使用新版本前缀：

- `v2.1:routes:{id}:comments:{cursorHash}`；
- `v2.1:safety-guides:{code}:current`；
- `v2.1:safety-agreements:{scene}:active`；
- `v2.1:user-settings:{userId}`。

要求：TTL 加 5%-15% 抖动；评论审核/下架、路线下架、指南发布和协议切版后写后失效；功能关闭判断在缓存读取前后均校验。评论计数如展示，只能由服务端派生，并增加对账任务；V2.1 P0 可不展示计数以降低一致性风险。

审核重试、协议/指南过期提醒和计数对账定时任务使用 Redis 分布式锁，记录失败指标并提供管理员人工补偿入口，不创建公开测试端点。

## 5. 安全与隐私

- 评论和反馈使用服务端纯文本 allowlist 清洗，拒绝脚本、事件属性、iframe、危险协议和外链图片；
- 所有写接口校验身份、用户状态、资源状态、所有权、输入、限流和幂等；
- 安全确认弹窗不得预勾选，不得用“继续即视为同意”；
- 格式条款中与用户有重大利害关系的内容需显著提示并可单独查看；
- 不收集与动作无关的身份证、健康、精确轨迹或紧急联系人；活动已有敏感字段应纳入最小化和访问审计；
- 日志不记录请求正文、评论/反馈全文、协议全文、token、openid、手机号或精确位置；
- 管理员预览敏感反馈须最小权限并记审计日志。

## 6. Prisma 增量迁移

只新增形如 `2026xxxxxxxx_v21_route_link_comment_safety_settings` 的迁移，不修改、合并或重命名历史迁移。

建议顺序：

1. 新建关系、评论、指南、协议、确认、设置和反馈表；
2. 给 `Activity`/`Route`/`User`/`AdminUser` 补 Prisma 关系，不改旧列语义；
3. 增加必要索引和外键；
4. 数据回填仅创建指南/协议草稿，不自动发布；
5. 空库执行全量迁移并校验 schema；
6. V2.0 数据副本执行增量升级，核对原表行数、外键孤儿、索引、耗时和锁等待；
7. 演练失败前滚：修复新迁移后追加迁移，不回滚已执行历史迁移；
8. 应用先以新增开关关闭部署，迁移完成并验证后再灰度开启。

## 7. 测试矩阵

### 单元/集成

- 路线下架、跨城市、伪造路线 ID、重复关系、并发创建；
- 评论屏蔽过滤、举报并发幂等、计数阈值、IDOR、XSS、重复提交、限流、举报不存在对象；
- 协议缺失、过期、哈希不符、场景不符、并发报名、事务回滚；
- 指南同人复核、缺来源发布、历史修订、来源失败和复核过期；
- 设置越权修改、系统权限与应用偏好混淆、缓存清理边界；
- 静态路由与 `:id` 顺序、错误响应和 request ID 兼容。

### E2E

1. 路线详情 → 发起同行 → 确认协议 → 发布 → 详情回看路线；
2. 路线详情 → 发起活动 → 另一用户确认协议并报名；
3. 提交路线评论立即可见 → 不同用户举报 3 次 → 进入待审核 → 后台通过或屏蔽；
4. 骑行安全手册 → 骑行应急知识 → 查看官方来源 → 提交反馈 → 管理员发布修订；
5. 设置偏好保存 → 重启回读 → 系统授权跳转 → 安全清理缓存；
6. V1 登录 → 无路线同行发布 → 报名 → 通知，验证兼容。

## 8. 可观测与发布

新增监控：路线绑定成功/冲突率、评论审核延迟/积压/失败、协议校验拒绝率、指南复核逾期、来源链接失败、设置保存错误率。所有指标按场景和错误码聚合，不使用用户标识作高基数标签。

发布顺序：迁移 → 后端（开关关闭）→ 管理后台 → 小程序测试构建 → 内容/法律复核 → 内部账号灰度 → 逐项开关。回滚时先关写开关，再清理 V2.1 缓存并回滚应用；新增表保留，不执行破坏性降级迁移。
