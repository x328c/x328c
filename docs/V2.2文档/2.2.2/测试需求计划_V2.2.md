### 1.2 重点测试清单

1. 新用户真实微信登录、协议版本匹配及首次资料创建。
2. Access Token 过期后的自动刷新、并发 401、Refresh Token 轮换及退出后的黑名单。
3. 同行报名并发时不超员；重复提交不重复增加人数。
4. 发起人取消/转让和普通成员取消报名的权限、时间边界、通知与计数一致性。
5. 集合地点与当前用户位置的距离计算、升序排序、半径过滤、分页总数。
6. 官方路线、本人私密路线、本人/他人公开路线均可正确关联同行。
7. 公开用户路线对其他用户可见，私密路线不可越权读取。
8. COS 上传凭证仅允许指定 Key 写入；匿名读取符合当前桶策略；匿名写入被拒绝。
9. “联系发起人”严格遵守微信号公开设置和同行关系。
10. 消息已读后列表红点和 TabBar 角标立即同步。
11. 安全倡议/事故指南无已发布内容时不影响法规列表。
12. 活动、论坛旧入口不可见，旧业务接口不允许继续写入。

### 1.3 不在本轮范围

- 支付、保险、导航轨迹实时记录等未实现能力。
- 微信、腾讯云平台自身可用性的内部测试；仅验证项目的调用、超时和降级行为。
- 历史活动/论坛业务恢复测试；仅验证退役兼容和无新增写入。

### 2.3 测试数据准备

- 城市：至少准备乌鲁木齐同城数据和一个异城市代码。
- 同行集合点：0.5 km、2.9 km、3.1 km、5 km、10 km、30 km、30 km 外各一条，用于边界测试。
- 同行人数：`1/2`、`1/10`、满员、即将出发、进行中、已结束、已取消。
- 时间边界：当前时间前后、出发前 2 小时边界、跨日、跨周。
- 用户路线：本人私密、本人公开、他人公开、他人私密、已删除、含/不含图片。
- 官方路线：已发布、未发布、已下线，不同难度和里程。
- 评论：纯文本、500 字、带 1–多张图片、重复幂等键、敏感内容模拟数据。
- 安全内容：无发布版本、单一发布版本、新旧版本切换、来源缺失/非法 URL。
- 文件：合法 jpg/png/webp，0 字节，伪装扩展名，超过 5 MB，超大像素图片。
- 通知：未读、已读、关联同行、历史退役类型各若干条。

## 三、测试策略

### 3.1 功能测试

#### 核心流程

- 登录 → 完善资料 → 浏览同行 → 发起/报名 → 通知 → 我的同行。
- 录入路线 → 设为公开 → 路线首页展示 → 评论/收藏 → 按路线发起同行。
- 浏览安全手册 → 查看来源 → 发起/报名时阅读并确认安全协议。

#### 边界条件

- 人数、时间、距离、字符串长度、图片大小、分页首尾页和空列表。
- 重复点击、并发请求、网络重试、幂等键重复或缺失。
- 创建者、成员、非成员、管理员不同角色权限。
- 软删除、下线、旧版本、Token 过期和功能开关关闭。

#### 自动化层次

| 层次 | 工具/方式 | 门禁 |
| --- | --- | --- |
| 后端单元测试 | Jest | 所有服务规则和异常分支通过 |
| API 集成/E2E | Jest + Supertest + 测试 MySQL/Redis | P0 API、鉴权、事务、迁移通过 |
| 前端静态检查 | TypeScript、ESLint/Stylelint | 类型检查无错误；新增代码不得增加规则违规 |
| 小程序构建 | Taro production/test build | 构建成功，4 Tab、分包和压缩门禁通过 |
| 管理后台 | TypeScript/Vite build + 人工回归 | 构建成功，权限菜单及核心操作通过 |
| 真机 | 微信开发者工具 + iOS/Android | P0 主链路与权限弹窗通过 |

### 3.2 兼容性测试

| 维度 | 最低覆盖 |
| --- | --- |
| iOS | 当前主流 iPhone 一台；最新微信正式版和前一个大版本 |
| Android | 小米/红米、华为/荣耀至少两个品牌；Android 10–当前主流版本 |
| 微信基础库 | 项目最低支持基础库、当前稳定基础库、开发者工具最新版稳定版 |
| 屏幕 | 小屏、刘海屏/挖孔屏、系统字体放大 |
| 网络 | Wi-Fi、4G/5G、200–500 ms 延迟、弱网、短时断网恢复 |

重点观察：定位权限、地图选点、相册/头像选择、图片上传、TabBar 安全区、分包首次加载和长文本布局。

### 3.3 性能测试

#### API 指标

| 类型 | 指标 | 测量条件 |
| --- | --- | --- |
| 列表接口 | TP99 ≤ 300 ms | 稳态、缓存正常、20 条/页；覆盖同行、路线、通知、法规 |
| 详情接口 | TP99 ≤ 200 ms | 稳态、缓存正常；覆盖同行、路线、法规和用户资料 |
| 写接口 | TP99 ≤ 500 ms | 不含微信/COS 外部网络传输时间；创建、报名、评论 |
| 错误率 | < 0.1% | 排除主动构造的 4xx |

压测应分别记录应用耗时、数据库耗时和外部接口耗时。同行“全城按距离排序”需使用接近预估峰值的数据量验证；若 TP99 超标，应改用数据库地理计算、边界框或 Redis GEO 分页，不能仅扩大超时。

#### 页面指标

- 已缓存主包的普通页面可交互时间：良好 Wi-Fi ≤ 1.5 s，常规 4G ≤ 2.5 s。
- 分包首次打开：良好 Wi-Fi ≤ 2.0 s，常规 4G ≤ 3.0 s。
- 用户点击后 100 ms 内应有视觉反馈；超过 1 s 的操作显示 loading。
- 主包和分包不得超过构建脚本预算：主包 1,200,000 字节，各分包 250,000 字节。

### 3.4 安全测试

- 登录 code 只能使用一次；客户端不得得到微信 `session_key`、AppSecret 或 COS 长期密钥。
- Access/Refresh/Admin JWT 使用不同密钥；校验签名、过期、Token 类型和 Redis 黑名单。
- 测试 IDOR：修改他人同行、删除他人路线/评论、查看他人私密路线均应返回 403/404。
- DTO 白名单开启，额外字段、非法 ID、超长文本和非法枚举应返回 400。
- API、后台和图片访问使用 HTTPS；证书链、域名、TLS 版本正确。
- 核对云磁盘、MySQL 卷和备份文件的静态加密/访问控制。当前业务字段未实施应用层字段加密，不得将“使用 HTTPS”等同于数据库敏感字段已加密。
- COS 临时凭证只允许指定对象 `PutObject`，过期后失效；匿名写入/删除必须拒绝。
- 上传校验 MIME、文件头、大小、尺寸和 Key 归属，不能仅信任扩展名。
- 日志不得记录密码、JWT、微信 AppSecret、COS Secret、微信号全文或法规正文。
- 管理后台高风险删除操作需角色校验、原因、二次确认和操作日志。

| SAFE-006 | 后台创建→他人复核→发布新版本 | 前台只展示新版本，旧版本历史保留 | P0 |
| SAFE-007 | 发起/报名同行拒绝安全协议 | 不创建业务记录和接受记录 | P0 |
| SAFE-008 | 接受安全协议后提交 | 记录用户、场景、目标、版本哈希、请求 ID、幂等键 | P0 |

## 五、验收标准

### 5.1 功能完整性

- 所有 P0 用例 100% 通过；P1 用例通过率不低于 98%。
- 微信登录、同行创建/报名/取消、路线录入/公开/关联、COS 上传、安全确认无阻断缺陷。
- 数据库迁移可从上一生产版本顺序执行，迁移后 Prisma 状态为 up to date。
- 活动/论坛入口不可见，旧写接口不可继续产生数据。

### 5.2 性能

- 列表 API TP99 ≤ 300 ms；详情 API TP99 ≤ 200 ms。
- 页面可交互时间符合 3.3 节标准；所有等待超过 1 s 的操作有反馈。
- 主包、分包通过项目包体门禁；无持续内存增长和重复网络轮询。

### 5.3 UI/UX

- 设计宽度 750 下无明显溢出、遮挡、按钮不可点或安全区覆盖。
- 状态颜色一致：报名/进行/结束/取消有可辨识底色；“已报名”置灰。
- 空、加载、失败、无权限、下线状态都有明确反馈，不白屏。
- 定位、头像、图片、订阅消息等权限在用户触发场景请求，并解释用途。
- 已读角标、报名人数、收藏数等状态在操作完成后立即同步。

## 六、缺陷管理

### 6.1 缺陷等级

| 等级 | 定义 | 示例 | 处理时限 |
| --- | --- | --- | --- |
| P0 | 核心流程不可用、数据丢失/泄露、越权、生产不可部署 | 无法登录、报名超员、私密路线泄露、迁移失败 | 立即阻断发布，优先修复 |
| P1 | 主要功能错误但有有限绕行，或明显兼容/性能问题 | 距离筛选错误、上传失败、角标不同步 | 当前版本修复并回归 |
| P2 | 次要功能或特定场景问题，不影响主流程 | 个别机型布局、非核心提示错误 | 评估进入当前或下一迭代 |
| P3 | 轻微文案、视觉一致性或优化建议 | 间距、措辞、日志可读性 | 纳入需求池 |

### 6.2 处理流程

1. 提交缺陷：环境、版本/Commit、账号角色、前置数据、步骤、实际/预期、日志和截图。
2. 分级与指派：产品、测试、开发共同确认严重度和影响范围。
3. 修复：关联代码、迁移和配置；高风险修复提供回滚方案。
4. 自测：开发执行针对性测试和静态检查。
5. 回归：测试验证原场景、相邻流程、权限和数据一致性。
6. 关闭：记录修复版本；不能复现需保留证据和观察期。
7. 复盘：P0/P1 数据、安全、生产事故必须形成原因与防复发措施。

缺陷单禁止包含真实 Secret、JWT、微信号、手机号和精确位置；必要日志须脱敏。

## 七、测试通过标准

### 7.1 通过率要求

- P0：100% 通过，且无未关闭 P0/P1 缺陷。
- P1：≥ 98% 通过；未通过项必须有明确责任人、计划和不影响发布的证据。
- P2/P3：记录在遗留清单，可按风险延期。
- 后端全部 Jest 测试、构建、Prisma 校验通过；前端类型检查、生产构建、包体检查通过；管理后台生产构建通过。
- iOS 和 Android 至少各完成一轮真机核心流程。

### 7.2 遗留问题原则

- 不接受通过关闭功能开关掩盖 P0 数据/安全问题后直接发布。
- P1 只有在存在可靠绕行、影响用户有限且产品/技术负责人书面接受风险时可延期。
- 所有延期项必须记录影响范围、监控方式、负责人、修复版本和最晚日期。
- 发布后对登录失败率、API TP99/错误率、COS 上传失败率、报名失败率进行重点观察。
